# Agent Note: session-username-identity-bind

Status: implemented

## Problem

Board card: "factory_reset + reprovision leaves stale session user_id". Re-verification on current Dev showed two distinct layers: (1) factory_reset alone is benign today — users.id is INTEGER PRIMARY KEY AUTOINCREMENT so re-seeded accounts get NEW ids and a stale session user_id resolves to no row, hitting the existing session.clear()→/login path (the card's original test-order symptom, still reproducible with session-scoped pytest clients); (2) a worse unrecorded hole: backup_quick_restore and restore_full swap the entire DB file, so a live session's user_id can reappear under a DIFFERENT username with different role/grants — full cross-user impersonation was reproduced (session 'zorica', id=3, acted as the restored row 'milan' and reached his /rent/contracts with 200) because nothing re-validated the session identity against the row.

## Decision

qp_crm/shared/web.py: both require_role and require_module now re-validate the session's stored username (written at login since Phase 3 step 3: session["username"] = user["username"]) against the user row resolved by get_user_by_id(user_id) on every gated request; on mismatch they clear the session and redirect to the unified login, same as the existing missing-row path. The check sits after the None-row guard and before the role/grant checks in both gates. Negative guarantees: the bind compares ONLY username (not a server-side session token or epoch — a same-named re-created account still reuses a live cookie, acceptable because re-created accounts get fresh ids under AUTOINCREMENT and factory_reset is admin-only); API-key authentication (/api/v1) is untouched; login/logout and session cycling are untouched. Deployed to the qp-crm container (commit 97e5be4); full test suite green (356 passed, 3 skipped). Both failure modes were reproduced empirically before the fix: stale user_id=3 'zorica' session acted as restored row 'milan' (200 on /rent/contracts with his grants) pre-fix, 302→/login post-fix.
## Alternatives considered

**Global auth_epoch in global_settings (bump on reset/restore, store in session).** Lost: needs a new setting write on every destructive admin action plus a session field, more machinery for exactly the same coverage; the username is already in the session and already identifies the row. **Explicit-id re-seeding in factory_reset (keep ids stable).** Lost: fights AUTOINCREMENT (sqlite_sequence keeps climbing), doesn't help the restore paths at all, and stable ids are exactly what makes stale cookies dangerous. **Test-side hardening only (restore users table around the factory_reset test).** Lost for this change: leaves the production impersonation hole open; the test landmine is real but cosmetic (302 instead of 200) and documented as follow-up on the board card.
## Consequences

Bought: closed a real impersonation hole (session surviving a DB-file restore acting as a different user with that user's grants); factory_reset and every gated request now verify the session identity against the row, not just the id. Cost/bought side note: test-order behavior is unchanged in shape — a session-scoped client created before the factory_reset test still gets 302 afterwards (row ids moved); the suite currently passes because login fixtures authenticate through the real login and no test depends on a pre-reset client surviving the reset, but any future test relying on that ordering will see 302→/login (documented on the board card as follow-up). The username comparison adds one string compare per gated request (negligible). Negative guarantees: sessions lacking a username (hand-crafted in tests) now fail closed — re-authenticated instead of passing; restore_full's file-swap mechanism itself is untouched, so sessions are killed but the restored data is still trusted as-is; user_modules grants are re-read per request as before.
