# Agent Note: qp-crm-dsh-sandbox-setup

Status: implemented

## Problem

QP-CRM (Flask CRM, freshly cloned from Dev branch) had to be set up and started inside a DSH workspace sandbox. Its own bootstrap script run_apps.sh assumes a root-capable machine: it runs `sudo apt install` (guarded by `set -e`) for WeasyPrint's native libraries and then creates a venv with ensurepip. In this sandbox sudo is blocked by the kernel "no new privileges" flag, `python3.12-venv`/ensurepip is missing, and there is no system pip3 — so the script aborts at the apt step and plain `python3 -m venv` fails too. Additionally WeasyPrint needs libpango system-wide, which no pip package provides.

## Decision

Environment is prepared root-free as follows: `python3 -m venv --without-pip venv`, pip bootstrapped via curl of get-pip.py run with the venv's interpreter, then `pip install -r requirements.txt` plus Werkzeug (Flask 3.1.3, Pillow 12.3.0, requests, WeasyPrint 69.0, pypdf 6.16.2, python-docx 1.2.0, mammoth 1.12.1, lxml 6.1.3, Werkzeug 3.1.8). `markdown` is deliberately NOT a pip dependency: all sub-apps append `custom_libs/` to sys.path at runtime and import the vendored markdown 3.10.2 from there. `app_data/product_images/` is created manually (the shared SQLite DB app_data/pricing.db is auto-created by init_db calls in main.py on boot). The detached start was attempted exactly as run_apps.sh does it (`nohup venv/bin/python main.py > main.log 2>&1 &`) and fails deterministically before the server binds: offer/app.py:8 and rent/app.py:10 import weasyprint at module level, and WeasyPrint 69 raises `OSError: cannot load library 'libpango-1.0-0'` — the whole merged app cannot boot, not only the PDF features. This limitation is reported rather than worked around, per the task's explicit instruction; NO application code was modified. Unblocking requires root outside this sandbox: `apt install -y libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0 libgdk-pixbuf-2.0-0 shared-mime-info fonts-dejavu-core` (the PKGS list from run_apps.sh), then the same nohup start command. Operational caveats for this machine: restart_app.sh hardcodes /home/lazar paths and must not be used; never run any command containing the string "main.py" while run_apps.sh is executing, because its `pkill -f main.py` matches the full command line of anything else (it aborts at apt before reaching pkill in this sandbox, but the rule stands for root-capable machines).
## Alternatives considered

**Extract libpango .deb packages into a user prefix and inject via LD_LIBRARY_PATH.** Rejected: this is precisely the "hacking around it" the task forbids; it also silently diverges the runtime from every machine that runs run_apps.sh normally, and apt lists may be stale without a successful `apt update`. **Patch offer/app.py and rent/app.py to import weasyprint lazily inside the PDF routes.** Rejected twice over: the task forbids modifying application code, and it would mask the missing-dependency condition instead of surfacing it (PDF endpoints would 500 at runtime instead of the process failing fast at boot). **Create the venv with --system-site-packages or install pip via apt.** Rejected: nothing useful exists system-side (no pip3, no pango), and apt requires the root access that this sandbox denies.
## Consequences

Bought: a fully reproducible root-free Python environment recipe for this workspace that survives without python3.12-venv, plus precise knowledge of the single remaining blocker (one apt package set away from running). Cost: QP-CRM is NOT running on port 5000 (curl gives connection refused; PID nonexistent; main.log holds the traceback), so goals depending on a live instance are deferred until someone with root installs the pango stack; the get-pip.py bootstrap deviates from run_apps.sh's venv path, so a future `rm -rf venv` by run_apps.sh on a root-capable machine would rebuild it the upstream way — both paths produce equivalent venvs.
