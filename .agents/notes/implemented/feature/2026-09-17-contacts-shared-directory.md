# Agent Note: contacts-shared-directory

Status: implemented

## Problem

MH leads parties in four disconnected places: rent has its own rent_clients (companies only), poslovi has the P4 customers spine (billing-focused, companies), and suppliers/employees/external collaborators have no registry at all. The user asked (P5-pre card) for an independent shared directory app that rent, ponude, poslovi and future radni nalozi all read — with supplier flag, fizičko lice support, "all options from the klient module in rent", plus zaposleni and spoljni saradnik.

## Decision

A new blueprint module `qp_crm/contacts/` mounted at `/contacts` behind `require_module("contacts")`, wired in `qp_crm/main.py` (prefix `/contacts`) and `qp_crm/wsgi.py` (boot init after deals). DDL lives in `qp_crm/shared/schema.py`: `create_contacts_tables` makes three tables — `contacts` (one row per party; `kind` ∈ {company, person} from `CONTACT_KINDS`; `display_name` is THE master name for both shapes; person fields first_name/last_name/jmbg, entity fields pib/mb/account; optional `user_id` → users(id) for the employee→nalog link and `customer_id` → customers(id) for the client→P4-spine link), `contact_roles` (rows, PK (contact_id, role), values from fixed `CONTACT_ROLES` = client | supplier | employee | external_collaborator | partner | other) and `contact_links` (additive contact↔customer/location attachments with relation/is_primary; a location must belong to its customer — enforced in `contact_service.create_link`). Business logic is in `qp_crm/services/contact_service.py` (list with search over display_name/first/last/pib/mb/jmbg/email/phone/city, ANY-of-roles filter, kind filter, archive-only — there is NO delete path for contacts, only links can be deleted). UI: list with role/kind/search filters, add/edit form with live person-vs-company field toggle, detail page with role badges and link management. Grants: `MODULE_CHOICES` gains "contacts" as version 4 (`CURRENT_MODULE_VERSION = 4` in shared/auth.py) — existing materialized staff accounts receive the grant exactly once on next boot via the version-aware seed; Admin → Users renders the new checkbox automatically. Rent integration: `/rent/contracts/new` picker merges legacy `rent_clients` with directory contacts holding the client role (directory ids are `c<id>` strings; `/rent/api/client/<ref>` accepts both and maps directory fields onto the legacy autofill JSON), and the rent banner gains a Directory link. Landing page gains the Imenik card behind the grant. NOT done (deliberately): offer-side picker integration, customers-table backfill, API v1 endpoints, migration of rent_clients rows into contacts — those are follow-up cards.
## Alternatives considered

["**Fork of the P4 customers table** (add kind/role columns to `customers`): rejected — customers is the deal/billing spine with derived statuses and invoice snapshots; bolting suppliers/employees onto it would pollute pipeline stats, reminders and invoice pickers with non-buyers, and a person-only client has no PIB/MB at all.", "**Two parallel tables (`contacts_companies` + `contacts_persons`) with a UNION view**: rejected — every picker, search and link row would need the union join forever; a new party shape (e.g. department) would mean a third table. One table with a `kind` discriminator keeps all queries single-table.", "**Boolean role columns** (`is_supplier`, `is_employee`, ...): rejected — the list is open-ended by business reality (the user added roles twice during the design chat alone); a new role must be a value, not a migration + form edit. Rows in `contact_roles` make 'several roles at once' trivial and the fixed tuple keeps the gate closed.", "**Merge rent_clients INTO contacts now**: rejected for this card — rent_contracts still carries its own client_* snapshot columns and legacy rows work; the picker merge is non-breaking and the full data migration belongs to the P5 rent-unification task with its own rename/merge tooling.", "**Put directory screens inside the deals app** (`/deals/contacts`): rejected — the user asked for an independent app (nezavisna app); rent staff without the 'deals' grant still need suppliers/collaborators, and deals' customer screens stay billing-focused."]
## Consequences

Bought: every module can now pick a party from one directory — rent contract forms already do; suppliers, employees (with login-account link) and external collaborators have a real registry instead of note fields; fizička lica enter the system with full identity fields. Grants v4 rollout means zero admin action to give existing staff the app. Cost: rent_clients is now a second client source — same-name dedupe in the picker is name-based only, and full unification (backfilling contacts from rent_clients + redirecting rent CRUD) remains open as the P5 rent-unification task; the employee->nalog link is one user_id per contact (an account with several directory entries is not representable); contact links resolve names via JOIN, so archived customers still resolve but new links should target active ones. Negative guarantees: no delete path anywhere in the module (archive only); issued documents are never rewritten from directory edits; the role/kind lists are closed — extending them is a schema-constant change, not free-form input; the API v1 surface is unchanged (no contacts endpoints yet).
