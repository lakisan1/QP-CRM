# Agent Note: location-postal-country-fields

Status: implemented

## Problem

User request: location (site) fields were Naziv/Adresa/Grad/Kontakt osoba/Telefon — add Poštanski broj (postal code) and Država (country). The default site is the contact's main address (2026-09-24 model), so the main address needs the postal code too, not just the extra-site table.

## Decision

`contact_locations` gained `postal_code TEXT` and `country TEXT` — via canonical CREATE in qp_crm/shared/schema.py AND idempotent `add_column_if_missing` ALTERs in migrate_contacts (legacy DBs upgrade on boot). `contacts` gained `postal_code TEXT` (same dual path) so the DEFAULT site (virtual id 0 = main billing address) can carry a postal code too; its country stays contacts.country. `_CONTACT_FIELDS` whitelist includes postal_code; the contact form (contacts/form.html) renders it between Grad and Država. location CRUD (`create_contact_location`/`update_contact_location`) accepts and persists both fields; routes pass them from the form. `location_choices(contact_id)` and `resolve_location(contact_id, location_id)` return DICTS now (was tuples): {id, label, address, city, postal_code, country} — the default site resolves postal_code from contacts.postal_code and country from contacts.country. UI (contacts/detail.html): locations table gained Poštanski broj and Država columns; the "Dodaj lokaciju" form gained both inputs; the header Adresa line renders street, city, postal, country. Offer: /offer/api/contact/<id> autofill JSON gained city + postal_code at top level and full per-site dicts; picking a site fills client_address as "adresa, grad, poštanski" and overwrites the country field with the site's country; picking the blank (main) refetches country from the contact. Rent: the Adresa zakupa datalist suggestions now include postal code ("adresa, grad, poštanski"). Suite: 356 passed.
## Alternatives considered

["**Postal code + country only on contact_locations, NOT on contacts** (keep main address as street+city+country only): rejected — the default site is what documents snapshot; without contacts.postal_code the main address can never print a postal code, making the extra fields second-class on exactly the majority case (1685 single-address parties).", "**Reuse contacts.country for locations instead of a per-site country column**: rejected — extra sites are routinely in OTHER countries (border-region clients, summer rentals abroad); a site-level country is the fact being stored, inheriting from the contact is only the default-site behavior.", "**Split postal_code into a normalized numeric column / separate city-zip table**: rejected — CRM treats addresses as free-text snapshots (existing convention); enforcement would break paste-from-invoice flows and offer no querying benefit at this scale.", "**Extend the E2E rent 'Adresa zakupa' into a strict select like the offer**: rejected — rent_address is printed on the contract and users type variants (gate numbers, 'iza zgrade'); the datalist suggests without constraining (snapshot-first rule)."]
## Consequences

Bought: both the default site AND every extra object can now carry a complete postal address (street, city, postal code, country) that flows into the offer/rent address snapshots on pick; the detail table and add/edit forms show the full picture; the migration is idempotent and already applied to the dev DB. Cost: contact_locations gains two mostly-empty columns on legacy rows (7 imported sites have neither value) — acceptable, NULL renders as '—'; the offer site JS joins address parts with ', ' so the client_address snapshot format changed slightly (postal code now appended when present) — historical documents are untouched (snapshot rule), only newly issued ones reflect it; rent datalist values changed shape the same way. Negative guarantees: no backfill infers postal codes from city names; the main address's postal_code lives ONLY on contacts (locations table never stores the default site); resolve_location still returns None for another contact's site (cross-party guard unchanged); POST edit route for a location of an unknown id still redirects to the list, not an error page.
