# Agent Note: musterije-directory-import

Status: implemented

## Problem

A 2024-2026 customer export (2181 rows, ; separated) needed to become ONE contact per customer in the QP-CRM shared directory (contacts/contact_locations), with repeated customers merged and multiple distinct addresses kept as locations, not duplicate contacts. The export is dirty: streets sit in the grad column, postal codes are glued to city names, phones/emails/JMBGs/JIBs appear in address columns, PIB/MB columns are swapped on several rows, some names are bare emails, and 9 rows embed 'Kupac: X Adresa: Y' in the name. A naive INSERT-per-row would have manufactured ~2200 contacts with hundreds of duplicates of the same party.

## Decision

scripts_import/import_musterije.py is the single entry point (--dry-run / --apply, CSV at app_data/imports/musterije.csv). Identity key per row: PIB (9-digit) → MB (8-digit Serbian or JIB from BIH rows) → fold()-ed display name; fix_pib_mb() corrects the export's 8/9-digit column swaps. Two-phase grouping: initial PIB/MB/name grouping, then an MB-collapse pass merges groups sharing one MB when any names are fold-similar (containment) — unrelated names sharing an MB stay separate. Each group produces ONE contact; master row = legal-form name first, then field richness; other name variants go to notes as 'Ostali nazivi u izvoru'. Distinct (address, city) pairs with a non-empty street become contact_locations (name=city, notes='Iz uvoza musterije 2024-2026'), never duplicating the billing street (substring-normalized both ways). Apply-side: existing directory contacts match by PIB/MB/folded-name and are enriched with empty fields ONLY (never overwritten) via _enrich(); new rows INSERT directly with one commit. Cleaning rules (all logged in the run report): 'Kupac: X Adresa: Y' name parsing, bare-email naziv → capitalized local-part + email kept, 'JIB x' naziv → MB + email-derived name, '0'/junk naziv → company name promoted from adresa; email/phone/JMBG/JIB/LK/OIB/BM/EMBS/company-number markers extracted out of adresa/grad into their proper fields; 'street, city' and postal-glued grad strings split or stripped; phones merged with prefix/digit-normalization keeping the longer form; junk '/ /' cells dropped. All decisions visible in the run report (34 counters). NOT done: no country for Montenegro/Kosovo rows (city carries them), no PIB checksum validation, no re-linking of offers/rent_contracts beyond what link_documents_to_contacts already did.
## Alternatives considered

**Import via contact_service.create_contact per group.** Lost: the service opens and closes one connection per call, so 2156 groups pay 2156 connection setups and the whole run is not one transaction; a mid-run crash leaves a half-directory. The importer instead opens one get_db() connection, writes contacts + roles + locations in it, and commits once — while reusing the service's conventions (archived=0, role rows, created_at ISO).

**Group strictly by PIB.** Lost: the export carries rows whose PIBs differ by one digit (AMK BUDUĆNOST-TURING, LOGISTIK CENTAR KRON) yet share the matični broj and address — keying by PIB alone manufactured two contacts for one customer. Key = PIB, then MB, then folded name, plus a separate MB-collapse pass that merges groups sharing an MB **only when names are similar after fold**; Emil Frey and GUMATRAK share an MB but are unrelated names, so they stay separate — a wrong identity must never swallow a real customer.

**Trust the export columns as-is.** Lost: adresa/grad are systematically shifted (street in grad for 160 rows, postal glued to city, city in adresa, phone/email/JMBG/JIB/IDs smuggled into either column). Half-measures were tried and removed iteratively: a looks_street() guard on postal-stripping ate real streets, and a person-name heuristic matched 2-word city names. Final rules require a 3–6 digit postal block for stripping, exclude 'bb' tokens from person heuristics, and gate swaps on CITY_TOKENS derived from the export itself.

**Write 'šifra banke' into contacts.account.** Lost: the column holds the client-code registry ('P-172'), not an IBAN — polluting the account field would print it as 'Broj računa' on detail pages; it goes to notes as 'Šifra klijenta: X' instead.
## Consequences

Bought: a clean 2156-row directory with zero duplicate PIBs/names, 20 pre-existing contacts enriched (empty fields only), 7 genuine multi-address sites as contact_locations, idempotent re-runs (created=0, linked=2157). Cost: ~20 rows keep source junk in notes rather than being silently dropped (auditable, not deleted); one source conflict (Emil Frey/GUMATRAK sharing MB 20586486) is preserved as two contacts for manual review; CITY_TOKENS covers the export's cities — new imports from other regions would need the set extended before dedupe of city-slots works as cleanly; country inference is coarse (BiH by JIB/length, else Srbija — Montenegro/Kosovo rows carry their city, not country).
