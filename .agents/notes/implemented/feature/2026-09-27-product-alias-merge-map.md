# Agent Note: product-alias-merge-map

Status: implemented

## Problem

The product catalogue has 254 rows and 31 prefix-pair duplicates under canonical comparison (e.g. "BODYGUARD 1.2" / "BODYGUARD 1.2 Spoljasnja verzija"). Renames are already safe because every row references products by id and issued documents keep their own line snapshots, but merging two duplicates collapses two rows into one concept, and the archive-only rule forbids deleting the merged-away row. Nothing existed to express "these two catalogue rows are one product" or to resolve an old name back to the surviving row, so any merge tool built on the P5 blueprint would have had to destroy history or invent an ad-hoc mapping.

## Decision

`product_aliases(id, alias TEXT NOT NULL UNIQUE, product_id NOT NULL REFERENCES products(id), created_at)` is created by `create_product_aliases()` in `qp_crm/shared/schema.py` (plus a `product_id` index) and is called from `create_pricing_tables()`, so pricing_init_db, wsgi.py, main.py and tests/conftest.py's temp_db all get it with no extra call site. The service is `qp_crm/services/product_alias_service.py` (data + service layer only; no routes/UI in this batch). `normalize()` is the single comparison key: NFKC, strip, collapse internal whitespace, casefold; None/blank -> "". `add_alias(alias, product_id)` checks the product exists (so the enforced FK never fires), rejects a blank alias, rejects an alias that equals a LIVE product's own canonical name (ambiguous), rejects an alias already owned by a different product, and is idempotent for the same alias->same product pair (returns the existing row id, writes nothing). `resolve_name(name)` matches a live product name first (indexed `COLLATE NOCASE` probe, then a normalized scan for whitespace/Unicode folds SQLite cannot express) and the alias table second -- with one deliberate exception: when a name is BOTH a live product name and an alias of a different product it can only be a merge's source, and there the alias wins, otherwise the merge would not resolve. `merge_products(source_id, target_id)` runs one connection/one commit: validates both rows and source != target, refuses a side whose own name already resolves elsewhere (no alias chains), inserts the source's canonical name as an alias of the target (bypassing add_alias's live-name guard on purpose), re-points every EXISTING products(id) reference column among `prices.product_id`, `offer_items.product_id`, `equipment.product_id`, `stock_movements.product_id`, `reservations.product_id`, `equipment_shortfalls.part_product_id`, re-points aliases that pointed at the source onto the target, and leaves the source row (id, name, all its prices) untouched. Its second return element is a summary dict `{source_id, target_id, alias, alias_id, repointed: {table.column: rows}, aliases_repointed, skipped: {name: reason}, message}`; failures return `(False, "string reason")`. `group_duplicate_suspects()` is a pure read (connection closed before grouping) doing transitive union-find over normalized equality-or-prefix relations, returning groups `{key: shortest normalized name, kind: "equal"|"prefix", size, products:[{id,name,item_type,tracking_regime}]}`; on the live catalogue it reproduces exactly the 31 known prefix pairs inside 17 groups. Negative guarantees: no alias ever points at another alias (product_id is a products row), no reference-like column is touched silently, no row anywhere is deleted, and no DDL lives outside shared/schema.py.
## Alternatives considered

**Rename the merged-away source row (e.g. append "(spojen)") and keep resolve_name purely name-first:** rejected because it mutates the row the archive-only rule wants preserved, and it would still need a uniqueness dance to pick a free suffix; the alias-over-a-live-name exception achieves the same resolution while leaving the source row byte-for-byte intact.

**Alias table the blueprint sketched (`alias_id PRIMARY KEY REFERENCES products(id), canonical_id`):** rejected in favour of the task's name-keyed `alias TEXT UNIQUE`; resolving by name is what renames/merges actually need (callers have a name, not the dead id), and `UNIQUE` on a brand-new table is safe because there are no legacy rows.

**Mark merged sources with a new `products.merged_into_product_id` column:** rejected as unrequested schema scope creep; the collision rule (live name that is also an alias loses) already disambiguates, and adding a products column would widen the blast radius of the already-fragile `ALTER TABLE products RENAME` migration path documented in `2026-09-27-shared-boot-init-sequence.md`.

**Re-point prices too or not at all:** prices IS re-pointed (merge must give the canonical row the whole price history and no row is deleted); the deliberate non-repoints are snapshots (`offer_items.item_name`, `*_name_snapshot`), `products.site_product_id` (references site_products, not products) and `products.product_code` (free text) -- all named in the summary's `skipped` map rather than dropped silently.

**Return `(ok, human_string)` like the contact/warehouse services:** rejected because the task requires per-table re-point counts; the second element is a dict (with a ready `message` key) on success and a plain string on failure, documented in the docstring.

**Auto-merging the 31 detected suspects:** rejected -- irreversible automation on real catalogue data; this batch only surfaces them via the read model.
## Consequences

The change is additive: `product_aliases` is a brand-new table, `create_pricing_tables` gains one call, and no existing query, route or template is modified, so the 404-passed/3-skipped baseline is unchanged plus 23 new tests in `tests/pricing/test_product_aliases.py`. Cost/obligations: (1) `merge_products` is service-only and unreachable from any UI — a future merge tool must call it and must handle the mixed success (dict) / failure (string) payload; (2) the re-point list is duplicated knowledge in `PRODUCT_REFERENCE_COLUMNS`; a future products(id) column must be added there or merges will silently leave it behind (the `skipped` report is the mitigation, not a guarantee); (3) `resolve_name`'s alias-wins-on-collision rule means an alias created before a later product takes that same name shadows the new live product — accepted because add_alias refuses that creation at the time, and because the reverse rule would break every merge; (4) `product_aliases` is one more child table of `products`, so it inherits the SQLite `ALTER TABLE ... RENAME` foreign-key rewrite that currently breaks the suite (see `2026-09-27-shared-boot-init-sequence.md`) — any future rename/rebuild of `products` must rebuild or re-point this table too. Named coverage gap: nothing prevents two products whose normalized names are equal-or-prefix from both existing (the unique index is `name COLLATE NOCASE`); `group_duplicate_suspects` only reports them, by design. Full-suite status at commit time: the committed tree was red before this change because of the bootstrap test blocker — with that one file excluded the suite is 404 passed/3 skipped at HEAD and 427 passed/3 skipped with this change.
