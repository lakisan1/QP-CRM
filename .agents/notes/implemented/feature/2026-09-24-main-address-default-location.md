# Agent Note: main-address-default-location

Status: implemented

## Problem

User question: should locations/sites replace the default address, now that only 7 contact_locations rows exist among 2156 imported contacts (1685 with a main billing address)? If someone has a second object, should the default just be the address with extras added on demand? User confirmed: main address = default location, extras only for multi-object parties — and asked for a container reboot after.

## Decision

`contact_service.MAIN_LOCATION_ID = 0` — a contact's main billing address (contacts.billing_address + contacts.city) IS the default site, resolved live, never stored in contact_locations. `location_choices(contact_id)` returns [(id, label, address, city)] with the default FIRST (id 0, label "Glavna adresa", present only when the contact HAS a billing address) followed by real contact_locations rows; `resolve_location(contact_id, location_id)` maps None/""/0 to the main address, a real id to the site row — an unknown id or a site belonging to a DIFFERENT contact returns None (cross-party guard).

Consumption: `/offer/api/contact/<id>` (qp_crm/offer/routes/core.py) gained a `sites` array in its autofill JSON; the offer form's new "Lokacija" select (id site-select, above Adresa musterije) is populated client-side after the musterija pick — choosing a site overwrites the client_address snapshot field (city appended: "adresa, grad"), clearing it refetches the main address; blank remains the default. The rent contract form's "Adresa zakupa" gained a datalist fed from the same model via /rent/api/client/<ref>'s new `sites` payload — suggestions only, the field stays a free snapshot (datalist not select, because rent_address is printed on the contract and may need typing).

UI: the directory detail page's Lokacije card now renders "⭐ Glavna adresa (podrazumevana)" as the first row (highlighted, read-only, with a link to the contact edit form), followed by extra objects; empty states explain the model. contact_locations schema UNCHANGED (7 imported rows stay); no migration needed.
## Alternatives considered

["**Promote every contact's main address into a contact_locations row** (import-style, one row per address): rejected per user decision — 1685 single-address contacts would each carry a redundant row duplicating billing_address; two copies of the same fact drift apart the first time someone edits one of them.", "**Documents store location_id FK**: rejected — offers/rent_contracts already carry the address as an issuance-time snapshot (client_address / rent_address); adding a location_id link would re-introduce the deleted deal-spine's site-picker complexity for zero current need — the site a document happened at is fully described by its frozen address snapshot.", "**Make the default site a real row with a UNIQUE(contact_id) 'is_default' flag**: rejected — UNIQUE-with-flag in SQLite means a second default row becomes possible the moment the flag discipline slips; a virtual id resolved live from the contacts row cannot drift by construction.", "**Global site picker (all locations across contacts) in the offer form**: rejected — a site only makes sense AFTER the party is picked (sites belong to the contact); a global list would leak other parties' addresses into the wrong form."]
## Consequences

Bought: the 2026-09-24 question "should sites replace the default address?" is answered in data-model terms — one fact, one home; the imported single-address majority is invisible in the locations table (zero noise); extra objects are opt-in and only appear in pickers when someone actually adds them; picking a site writes the snapshot field exactly like free typing does, so PDFs and issued documents behave identically either way. Cost: location id 0 is a SENTINEL — any future consumer storing a location reference must accept that 0 means "resolve the party's current billing address live" (and that the resolved value moves when the contact's address is edited, unlike a frozen document snapshot); the offer site select is client-rendered (populated by JS from the autofill payload) so it is empty until a musterija is picked — server-side validation of a chosen site does not exist (the chosen site only feeds a text field, never a stored id). Negative guarantees: resolve_location NEVER resolves another contact's site (cross-party guard, tested); the default site is not a contact_locations row (COUNT(*) there stays 7 from the import); rent's Adresa zakupa has no strict select — the datalist suggests, the field stays free.
