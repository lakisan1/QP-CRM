# Agent Note: invoices-payments-spine

Status: implemented

## Problem

The P4 deal spine ended at 'won': an accepted offer could not become money. The user confirmed (2026-09-16) that invoices use ONE GLOBAL per-year sequence (F-YYYY-NNN), unblocking the financial tail: invoices issued from accepted offers, payments recorded against them, and a derived 'paid' deal status.

## Decision

Shipped in qp_crm (commit a0cbd1a on Dev, container rebuilt + restarted via deploy.sh, image qp-crm:phase3, healthcheck green; live DB migrated idempotently on boot). Schema (shared/schema.py create_invoices_tables, reached through create_deals_tables so deals_init_db owns the boot): invoices (code UNIQUE, deal_id NOT NULL, customer/location/source_offer FKs, issue_date/due_date, currency + exchange_rate, total_gross, FROZEN client snapshot client_name..client_country, notes, created_at, voided_at), invoice_items (position/description/qty/unit/unit_price/discount_percent/line_total — offer math copied as-is), payments (paid_at/amount/currency/method/reference/note/created_by), invoice_counters (year PK) issuing F-YYYY-NNN from ONE GLOBAL per-year bucket — user decision 2026-09-16, supersedes OPEN_QUESTIONS #4. services/invoice_service.py: issue_invoice_from_offer (one LIVE invoice per offer; re-issue only after void), record_payment (positive amounts only; voided invoices closed; both write 'document' events on the deal timeline via _append_event — events are inserted on the CALLER's transaction because deal_service.add_event opens its own connection and dead-locks SQLite's single writer mid-transaction), void_invoice (idempotent; voided invoices drop out of the paid derivation and the thread section; payments remain in the DB for audit). Deal status derivation extended, never stored: closed > paid > won > offered > new, where paid = >=1 non-voided invoice AND all fully covered (SUM(payments.amount) >= total_gross; overpayment counts as covered). deal_with_offers returns (deal, offers, events, invoices, status); pipeline_board grew the 'paid' column. UI: deal thread Fakture section (issue-from-offer buttons with due date, per-invoice ukupno/uplaćeno/ostalo, inline payment form, Plaćena chip, Storno button), timeline links for invoice/void/payment, 5-column pipeline, .status-paid badge, deals filter includes Plaćeno. NOT done: invoice PDF documents, global /invoices list page, credit notes for overpayment, partial-payment status.
## Alternatives considered

**Storing paid/status on invoices**: rejected — every payment insert would have to remember to update it; derivation from SUM(payments) is cheap and always true. **Partial-payment status (partially paid)**: dropped — binary paid/not-paid; the remaining amount is visible in the UI. **Editing issued invoices**: rejected by blueprint §4 — issued documents are frozen; mistakes go through storno + re-issue (void is idempotent, keeps payments for audit, frees the offer for re-invoicing). **Calling deal_service.add_event from invoice transactions**: implemented first, dead-locked over HTTP ('database is locked' — add_event opens its own connection while the caller's is mid-transaction, SQLite single-writer); replaced with invoice_service._append_event on the CALLER's cursor. **Invoice gross from the offer row's total_gross**: rejected after HTTP testing — new_offer inserts total_gross=0 and it stays 0 until an edit recalculates; the offer ITEMS (SUM(line_net)) are the frozen math that actually shipped. **Per-customer/per-deal invoice series**: rejected — user explicitly chose one global per-year sequence. **Separate /invoices list page**: deferred — deal-thread-first keeps the workflow on one page; a global list can come when volume demands.
## Consequences

Bought: the deal lifecycle is complete end-to-end — issue → pay → paid is real; the pipeline board's Plaćeno column and the thread's Plaćena chip need no upkeep because they are pure reads over payments; voiding is safe (audit never loses rows); the offer-edit path stays untouched (snapshots frozen). Cost: invoice PDFs are NOT built (deal thread + timeline carry the data; a F-YYYY-NNN PDF template is an obvious P4.y follow-up); 'paid' recomputes per request (SUM per invoice per deal — fine at CRM volume, worth an index review if thousands of invoices appear); overpayment marks paid and keeps the extra payment (no credit-note logic); voiding a PAID invoice reverts the deal to won while its payments sit in the DB — that is the intended audit behavior but operators should know; deal_service.derive_status now pulls invoice_service (circular-import safe via function-level import). Coverage gap: no test for concurrent invoice issuance beyond the 3-retry guard (same accepted risk as deal codes); no test for multi-currency invoices on one deal (data model allows it, derivation requires ALL covered — currency mixing untested).
