# Agent Note: deals-spine

Status: implemented

## Problem

QP-CRM priced and offered ad hoc: offers carried a frozen client snapshot with no master data behind it, "which offers belong to which customer story" lived only in users' heads, and there was no place to hang the upcoming invoices/payments/stock phases. Phase 4 needed a deal spine (customers, locations, deals, timeline) without breaking the blueprint rule that issued documents are frozen point-in-time copies.

## Decision

Shipped in qp_crm (branch phase-4-deals, merged to Dev, tag qp-crm-phase4): `qp_crm/shared/schema.py` `create_deals_tables()` + `migrate_deals()` add `customers`, `customer_locations`, `deals`, `deal_events`, `deal_counters` (all idempotent, boot-order pricing→offer→admin→rent→deals) and `offers.deal_id`/`offers.location_id` via `add_column_if_missing`. `qp_crm/services/deal_service.py` is the single owner of deal logic: numbering `D-YYYY-NNN` per GLOBAL year bucket (`deal_counters` year PK, `INSERT..ON CONFLICT DO NOTHING` + `UPDATE..RETURNING`, `UNIQUE(code)` + 3-retry guard); statuses are DERIVED, never stored — `derived_status_for()` precedence closed > won (decision event `linked_doc_type='offer_accepted'`) > offered (≥1 linked offer) > new, with `_row_get()` because sqlite3.Row has no attribute access (the original `getattr()` made `closed` unreachable — caught by T6 tests); customers archive (`archived=1`), never delete; locations validate customer ownership; the timeline (`deal_events`, fixed EVENT_TYPES) records creation, document link/unlink (`record_offer_linked` from the offer routes), and the acceptance tap (`record_offer_accepted`). `qp_crm/deals/` blueprint (url_prefix `/deals`, `require_module('deals')`) serves customers CRUD, deals list/thread, and the read-only pipeline; offer routes gain Posao/Lokacija pickers, `?deal_id=` master-data prefill (pre-fill only — the issued client snapshot stays frozen), and link/unlink events written on change only. `MODULE_CHOICES`/`MODULE_INTRODUCED` grew the `deals` entry (v3 exactly-once rollout via `users.modules_set`). NOT done here: invoices/payments (won→paid remains unrepresentable until P4.x, blocked on invoice numbering format), PDF deal-code imprint, stock reservation links (P5).
## Alternatives considered

**Stored status column on deals** (status TEXT maintained by triggers): lost because it duplicates the truth the blueprint forbids — every code path that adds an offer or event would have to remember to update it, and history corrections become impossible. **Post-acceptance locks (block offer edits once accepted)**: deferred — real users reissue corrected offers after a verbal accept; forcing deletes/recreates breaks the audit trail. Revisit if drift complaints appear. **Invoice/payment entities inside P4** (would have completed won→paid): dropped — blocked on the user confirming the invoice numbering format (OPEN_QUESTIONS #4); deferred to a P4.x card. **Hand DELETE endpoints for customers/deals/events**: rejected per blueprint §4 — customers archive via `archived=1`, deals close via `closed_at`, timeline events are the audit trail (event deletion kept for fixing typos only). **getattr() on sqlite3.Row for closed_at**: the original implementation — lost because sqlite3.Row supports only item access, making `closed` unreachable; replaced by `_row_get()` item-access helper (found by T6 tests, fixed in e6d4334).
## Consequences

Bought: one spine under pricing, offers, and (future) invoices/payments — the pipeline board is a pure read over `offers`, so it needs no upkeep; customers/locations/deals are safe to edit forever (no cascade deletes anywhere); grant v3 propagated the module to existing staff without a data migration. Cost: statuses must be recomputed (cheap — indexed queries), hand events are deletable so a deleted acceptance event reverts a deal to `offered` (accepted, trade-off); the deal picker lists ALL deals including closed ones — filtering that is left until it bothers someone; `derive_status`'s `closed > won` precedence means reopening a closed deal after acceptance shows `won`, not `closed` (intended); per-user module grants + landing card + tests all assume `MODULE_CHOICES` order for the Users form (test_user_management now uses `list(MODULE_CHOICES)` — adding a module in P5 automatically extends those tests). Coverage gap: no characterization for `pipeline_board` SUM edge cases beyond the one currency case; stock availability across reservations is explicitly P5, not this note.
