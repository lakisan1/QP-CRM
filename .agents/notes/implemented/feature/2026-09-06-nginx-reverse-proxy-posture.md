# Agent Note: nginx-reverse-proxy-posture

Status: implemented

## Problem

Remote access was the last open security gap for the Phase-3 system: the app is plain HTTP on :5000, which is fine on a trusted LAN but not for users outside it. The operator decided the topology himself: the app keeps its own port behind an NGINX reverse proxy that provides HTTPS and the domain — and asked for a 'domain option' and an 'https-only toggle' on the docker-compose side, so the app had to learn to live correctly behind a TLS-terminating proxy (trust X-Forwarded-* for scheme/client-IP, mark the session cookie Secure, advertise https, send HSTS).

## Decision

QP-CRM supports the operator's chosen remote-access topology: the app stays on its own port 5000 inside the single container, and nginx (operator-managed) owns 80/443 with HTTPS + a domain. qp_crm/shared/tls.py (new, committed 7e71110 on phase-3-auth) reads two env vars at import: QP_HTTPS_ONLY=1 enables werkzeug ProxyFix(x_for=1, x_proto=1) around the WSGI application, SESSION_COOKIE_SECURE on qp_session, PREFERRED_URL_SCHEME=https, and an after_request that adds Strict-Transport-Security (max-age=31536000, deliberately WITHOUT includeSubDomains) only when request.scheme == 'https'; QP_PUBLIC_DOMAIN is stored as app.config['PUBLIC_DOMAIN'] and printed at boot with a note that it must match nginx server_name. Both default off/empty: wrap_wsgi returns the application unchanged and no cookie/HSTS flags are set, so plain-LAN-http deployments behave exactly as before. qp_crm/main.py calls configure_app(app) after the session config and exports application = wrap_wsgi(app); qp_crm/wsgi.py imports main.application, so gunicorn and bare-metal runs share the wrap. docker-compose.yml makes the published port bind configurable via QP_APP_BIND (default 0.0.0.0; set 127.0.0.1 once nginx fronts the app) and passes the two TLS vars (${QP_HTTPS_ONLY:-0}, ${QP_PUBLIC_DOMAIN:-}). .env.example and DOCKER.md document the recipe, including the nginx requirements the app depends on: proxy_set_header X-Forwarded-Proto $scheme (mandatory for ProxyFix), client_max_body_size 25m for photo uploads, and proxy_read_timeout 120s because WeasyPrint PDF rendering is slow. Tests (tests/security/test_tls_config.py, 6 tests) pin: defaults untouched; https-only sets the cookie/scheme flags and returns a ProxyFix wrapper; domain stored; HSTS + Secure cookie served over X-Forwarded-Proto https; no HSTS over plain http even when https-only=1; no HSTS when off even with a forged proxy header (ProxyFix absent). NOT done: nginx config/certs/domain (operator side — steps listed on the board card); no SERVER_NAME or host allow-listing; PUBLIC_DOMAIN has no functional effect beyond metadata yet.
## Alternatives considered

**Caddy as the TLS proxy** — earlier recommendation (auto Let's Encrypt in 3 lines) — rejected by the user: they already run/own nginx and prefer it. **VPN overlay (Tailscale/WireGuard)** for remote access — rejected: user chose a public reverse proxy with a domain instead. **SERVER_NAME / host-allowlist driven by the domain env** — rejected: would make Flask reject LAN IP access when SERVER_NAME is set, breaking the hybrid LAN+remote usage; instead the app trusts the proxy's Host via ProxyFix and never constrains hosts. **HSTS with includeSubDomains** — rejected: the operator's domain may host other plain-http services; max-age only is the conservative choice. **Unconditional (non-env) https hardening** — rejected: the app must keep working byte-identically on plain LAN http until the operator flips the toggle.
## Consequences

Cost: three new env vars on the operator's surface (QP_HTTPS_ONLY, QP_PUBLIC_DOMAIN, QP_APP_BIND) and one new import-time module (qp_crm/shared/tls.py) — all defaulting to today's behavior, so existing deployments are untouched until the env vars are set. ProxyFix trusts X-Forwarded-For from ANY client that can reach the app: if QP_HTTPS_ONLY=1 is set WITHOUT nginx in front, a LAN client can spoof X-Forwarded-Proto to gain the 'https' scheme and HSTS — QP_APP_BIND=127.0.0.1 (nginx only) is the documented counterpart that makes that unreachable. PUBLIC_DOMAIN currently has no functional effect beyond app.config metadata and the boot log — it exists so the operator names the domain in one place and docs link it to nginx server_name; a future card can surface it in templates (e.g., login-page canonical link). wsgi.py's top docstring still mentions the pre-Phase-2 DispatcherMiddleware merge (stale text, harmless). Bought: the operator's chosen nginx+domain+HTTPS topology is now supported with Secure cookies, correct scheme awareness (PDF/image/file:// downloads unaffected — they are same-origin relative links), HSTS, and a LAN-only :5000 once QP_APP_BIND flips; covered by 6 new tests in tests/security/test_tls_config.py; suite 251 passed, 3 skipped. The auto-backup feature was moved to Phase 4 (board card retitled), so nightly backups are not automated until then — the manual in-app download remains the backup path in the interim.
