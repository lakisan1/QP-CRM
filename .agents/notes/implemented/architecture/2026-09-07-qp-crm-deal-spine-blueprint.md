# Agent Note: qp-crm-deal-spine-blueprint

Status: implemented

## Problem

MH runs offers, invoices, ticketing, service docs and stock tracking across Office, an old CRM, ticketing software, accounting stock and an Excel sheet with zero links between them. QP-CRM (pricing/offer/rent/sale modules, unified auth, PDF engine) is being extended to centralise everything, and the user asked whether fitting the whole workflow into one app is realistic or a path to an unusable CRM mess.

## Decision

One `deal` per customer request is the spine: deals hang off a unified customers table; offers, invoices, payments, purchase orders, stock reservations, travel/work/service orders and signed PDFs all link to the deal; statuses are derived from linked documents, never hand-maintained except for `new`. Admission rule for every future feature: it must be a new document type on the deal, a view over existing data, or master data — anything wanting its own workflow engine or its own customer copy is rejected. Scope decisions confirmed by user: offers AND invoices are issued from the app (finance software stays for receipts/ePayment); fresh start for old data (no history import); operational stock ledger owned by the app; full equipment registry with serials + maintenance reminders; service techs work from phones with customer signing on-device; first release = customers + deals + offer/invoice.
## Alternatives considered

**Full accounting in-app (double-entry GL, stock valuation):** rejected — the finance software remains legal truth for receipts/ePayment; app mirrors invoices only. Overlaps the accountant and multiplies scope. **Generic CRM feature set (campaigns, lead scoring, custom-field builders, portal):** rejected — these are the workflow-multiplying features that make CRMs rot; every addition must name the workflow step it replaces. **Full history import from old CRM/ticketing:** rejected by user choice — fresh start; only customers are re-entered, historical stats stay in the MH fin analitike analytics DB. **Invoice PDFs generated by the app:** deferred — user currently issues offers/invoices from Word/Excel; the app takes over invoice issuance later, as it is the same document pipeline as offers (PDF template + items + totals + payment tracking). **Read-only stock mirror / accounting-grade stock:** rejected — user chose operational stock ledger owned by the app; a mirror would recreate the Excel-alongside-CRM antipattern.
## Consequences

Bought: all six scope decisions are decidable and recorded; phase 1 scope (deals+customers+offers link) is buildable on the existing schema without touching money-path services; the anti-mess rule is now a reviewable artifact, not a verbal agreement. Cost: five decisions remain open until the user answers (ticketing replacement, phases 2-3 ordering, host device for e-signature, foreign-currency stock, document archive policy). Phase numbering (P4) conflicts with the old roadmap's phase numbering unless renamed — naming decision pending.
