# Agent Note: qp-crm-deal-spine-blueprint

Status: implemented

## Problem

MH runs offers, invoices, ticketing, service docs and stock tracking across Office, an old CRM, ticketing software, accounting stock and an Excel sheet with zero links between them. QP-CRM (pricing/offer/rent/sale modules, unified auth, PDF engine) is being extended to centralise everything, and the user asked whether fitting the whole workflow into one app is realistic or a path to an unusable CRM mess.

## Decision

One `deal` per customer request is the spine: deals hang off a unified customers table; offers, invoices, payments, purchase orders, stock reservations, travel/work/service orders and signed PDFs all link to the deal; statuses are derived from linked documents, never hand-maintained except for `new`. Admission rule for every future feature: it must be a new document type on the deal, a view over existing data, or master data — anything wanting its own workflow engine or its own customer copy is rejected. Scope decisions confirmed by user: offers AND invoices are issued from the app (finance software stays for receipts/ePayment); fresh start for old data (no history import); operational stock ledger owned by the app; full equipment registry with serials + maintenance reminders; service techs work from phones with customer signing on-device; first release = customers + deals + offer/invoice.

Amendment (same day, user follow-up) — customers with several workshops and several concurrent deals. Three-level party model: `customers` (legal entity: PIB/MB, billing address — "who pays"), `customer_locations` (physical sites: address, site contact — "where work happens", nullable on deal: defaults to customer's registered address), `deals` (the thread — "when/what"). Deals are first-class and never merged by customer, so N concurrent deals per customer is already supported: each carries its own derived status, own documents, own stock reservations; customer-level totals are views, not stored state. Concurrency guardrails: document numbering stays global per type per year (deal has its own deal code D-YYYY-NNN for reference in emails); stock availability is computed across ALL active deals' reservations (available = on-hand − Σ reservations), so two deals wanting the same machine are visible, not silently overbooked; payments attach to a specific invoice (one payment may allocate across several invoices by amounts), never to "the customer account". Travel orders, work orders and equipment registry entries reference the location, not the customer HQ; equipment serials live at a location. Documents keep their issued billing snapshot (existing offer client fields stay) and additionally link `deal_id` for analytics — master data lives in customers/locations, documents snapshot at issuance.

Amendment 2 (same day, user follow-up) — device data must not fragment, and stock must not be invoice-bound. Single database, single `products` catalog (the pricing module's existing table): quotations, stock and the equipment registry all reference the same `products` rows — three views, never three stores. Trackable items split by kind: serialized goods (lifts, PTI lanes, testers) are tracked as `equipment` instances (serial no, current custodian: our warehouse / customer+location / supplier / scrapped, since-date, status incl. loan/test); consumables stay a quantity movement ledger — a serialized item is NEVER double-tracked as both qty rows and an instance (warehouse stock of serialized goods is derived from instances with custodian=our warehouse). Custody is the primary fact; documents are optional evidence: every stock/custody movement carries a nullable reference (offer/invoice/deal/PO) and a reason from a fixed list (purchase-in, sale, FREE-issue, LOAN, TEST/DEMO, return, service-in, transfer, scrap). "At that customer and since when" is answered by the movement/instance itself, no document required; revenue-per-machine analytics only uses movements that carry a document link. Loans get optional expected-return dates feeding the reminder engine; customer-owned machines arriving for service are registered as instances under our custody (reverse flow), so nothing at our premises is untracked. Deal reservations may pin qty (consumables) or specific instances (serialized units); the cross-deal availability check stays.

Amendment 3 (same day, user follow-up) — warehouse coverage loop and van stock. (a) Coverage/ATP view per product: available-to-promise = on-hand − Σ active reservations + Σ incoming ordered qty (expected date not yet passed); reservations are always "for whom" (deal → customer name + deal code, or free-text note for internal needs), so "what is reserved and for whom" is one query; supplier purchase orders are first-class rows (supplier, lines, expected arrival, status derived from receipt movements referencing the PO: ordered → partially received → received) and may be allocated to deals, making "orders needed" visible per product and per deal. No automatic procurement: the view highlights shortfalls, humans create POs. (b) Company vehicles are internal custodians, NOT customer rows: `fleet_vehicles` table (plate/name, optional default technician); movement custodian type set ∈ {warehouse, fleet_vehicle, customer_location, supplier, scrap}. A van is a mobile sub-warehouse: warehouse→van movements record "who took which spare parts", van holdings are derived from movements, unused parts return van→warehouse, and parts consumed at a customer go van→customer_location with the same reason list (free-issue/sale/service). Vans appear in the same custodian picker as customers — same UX, but customer stats, invoices and reminders stay clean because vans never enter `customers`.

Amendment 4 (same day, user follow-up) — conservation law and its honest escape hatch. Serialized goods: every instance row lives forever — rows are never deleted; a lift that leaves the catalog gets custodian=scrap (or sold-off-record), so "10 lifts bought in 2024" remains 10 rows for the company's lifetime and a lift can never silently vanish (a physical count mismatch on serialized goods is a loud incident, not a balance adjustment). Consumables: the qty ledger is arithmetic, not identity — 100 screws in, 30 issued, 70 on hand; no per-screw tracking, and counting happens in practical units of measure (box of 100, liter, meter) with an optional min-stock alert (reorder point) per product instead of per-unit discipline. Because real warehouses have shrinkage, the fixed reason list gains stocktake/adjustment (write-off, found surplus, correction): a periodic stocktake reconciles counted vs ledger quantity via an adjustment movement carrying a note — the ledger may be corrected, never faked by omitting movements. Practical floor agreed with user: serials are tracked faithfully (they're few and expensive); consumables are tracked loosely on purpose (they're many and cheap) — the model tolerates that asymmetry by construction.

Amendment 5 (same day, user follow-up) — tracking is opt-in per product; donor parts are debts, not inventory. Supersedes Amendment 4's implication that consumables are generally tracked. (a) Every product carries a regime flag: `untracked` (default for small parts — exists in the catalog for offers/invoices/POs only, NO stock ledger, no movements, no counts), `qty` (opt-in loose ledger for things worth counting — drums of oil, expensive spares; Amendment 4's practical-units + stocktake rules apply only here), `serialized` (identity tracking, mandatory for anything with a serial plate). Reservations and van holdings apply only to tracked regimes — an untracked part is invisible to stock by explicit choice; if a part class ever needs van accountability, its regime flips to `qty` and the existing machinery covers it. Boundary: QP-CRM is NOT the audit warehouse software — the audit system stays the counting/in-and-sold truth; this app tracks CUSTODY of machines and DEBTS between machines, not inventory value.

Amendment 6 (same day, user follow-up) — temp products everywhere; rename/merge without breakage. (a) The quotation "temp product" pattern becomes app-wide: a line/row references by id (nullable FK) AND carries its own text snapshot (name/description/photo). The quotation already does this (offer_items: nullable product_id + NOT NULL item_name). Warehouse gets the same option: movements and equipment registrations may run on a temp product (ad-hoc spare part, unnamed device) with NULL product reference + typed description; a "make real product" action promotes a snapshot into a catalog row and back-fills the references in one update. (b) Reference integrity by design: every module links entities by surrogate id and never by name, so renaming a product (or customer/location) is editing one master row — every view resolves the name live at read time, nothing breaks. (c) Merging duplicates (2 or 5 products — or customers — into one): `product_aliases` table (alias_id → canonical_id); merge = choose the target, insert alias rows, old ids keep resolving through the alias map (a UNIQUE index on alias ids prevents chain/diamond aliases — an alias may never itself be aliased); a maintenance view lists suspected duplicates (same/similar name, both referenced) and a merge tool re-points referencing rows to the canonical id at leisure. Same machinery reusable later for customers and locations (companies rename, get bought, duplicate under different spellings). (d) Snapshot nuance, deliberately NOT auto-updating: issued documents keep what was written at issuance (old offers show the old product name — they are legal records); only NEW lines/resolutions show the canonical name. Rename/merge therefore never rewrites history. (b) Donor/cannibalization workflow (take a part off device A to fix device B, order replacement later): tracked as a SHORTFALL — a small `equipment_shortfalls` row (device A, part name/product ref, taken-for deal/work order, date, nullable PO-line ref, closed_at) — not as part-level inventory (rejected: sub-assembly tracking is the complication the user refuses). Mechanic flow: on the work order, one tap "took part from device…" → pick device → type part → done; system flags device A as incomplete (visible on device page + coverage view), adds it to the orders-needed list, writes both timelines. Replacement arrives → tap "complete device A" (or auto-close when a PO line referencing the shortfall is received). Fallback if even that is too much: a plain timeline note is allowed — but then nothing reminds anyone that device A is half-dismantled and nothing hooks the replacement order, so the shortfall is the recommended two-tap version of the note.
## Alternatives considered

**Full accounting in-app (double-entry GL, stock valuation):** rejected — the finance software remains legal truth for receipts/ePayment; app mirrors invoices only. Overlaps the accountant and multiplies scope. **Generic CRM feature set (campaigns, lead scoring, custom-field builders, portal):** rejected — these are the workflow-multiplying features that make CRMs rot; every addition must name the workflow step it replaces. **Full history import from old CRM/ticketing:** rejected by user choice — fresh start; only customers are re-entered, historical stats stay in the MH fin analitike analytics DB. **Invoice PDFs generated by the app:** deferred — user currently issues offers/invoices from Word/Excel; the app takes over invoice issuance later, as it is the same document pipeline as offers (PDF template + items + totals + payment tracking). **Read-only stock mirror / accounting-grade stock:** rejected — user chose operational stock ledger owned by the app; a mirror would recreate the Excel-alongside-CRM antipattern.
## Consequences

Bought: all six scope decisions are decidable and recorded; phase 1 scope (deals+customers+offers link) is buildable on the existing schema without touching money-path services; the anti-mess rule is now a reviewable artifact, not a verbal agreement. Cost: five decisions remain open until the user answers (ticketing replacement, phases 2-3 ordering, host device for e-signature, foreign-currency stock, document archive policy). Phase numbering (P4) conflicts with the old roadmap's phase numbering unless renamed — naming decision pending.

Amendment consequences: `customer_locations` enters the P4 schema (one extra table + nullable location_id on deals/documents — small build cost, doing it later would mean a painful backfill of location semantics onto existing deals). Bought: multi-workshop and concurrent-deal realities are structurally supported instead of patched per-feature later; stock overbooking across concurrent deals becomes impossible by construction; per-location service history (P6/P7) is joinable from day one. Cost: every document form gains a site picker (one dropdown, pre-filled); P6/P7 "which site?" must be asked on travel orders, work orders, and equipment installations.

Amendment 2 consequences: schema now names `equipment` (serialized instances) and `stock_movements` with nullable doc references + fixed reason list as the single physical-goods model across all modules; P5 builds it and the pricing/offer modules keep using `products` untouched. Bought: "what is at which customer since when" is answerable without any invoice; free/loan/test dispatches are first-class, not hacks; the analytics DB's funnel stays possible via optional links. Cost: issue forms need a reason chooser (loan/test entries get an optional expected-return date); serialized warehouses lose qty-count rows (count is derived from instances); if the accountant ever needs invoice-line ↔ serial mapping for books, that is a reconciliation export, not app state — deliberately out of scope.

Amendment 3 consequences: P5 gains `purchase_orders`, `fleet_vehicles`, and custodian-type on movements/reservations; deal reservations carry a required "for whom" (deal link or free-text). Bought: the Excel's last two jobs — reserved/for-whom/ordered tracking and van spare-parts accountability — have real homes before P5 is built. Cost: PO receipt status must be derived consistently from movements (kept simple: receipt movements referencing the PO); van stock depends on the discipline of recording van→customer consumption, which the mobile P7 flow must make one tap. Rejected: modeling vans as customers (pollutes customer stats, reminders and invoicing with internal rows) — a parallel `fleet_vehicles` table with the same custodian picker UX won instead.

Amendment 4 consequences: the fixed reason list gains stocktake/adjustment; product master gains an optional min-stock field and practical units of measure; UI rule set: no delete button on equipment instances (only scrap/sell-off transitions) and no delete on movements (only a reversing movement). Bought: serialized stock is conserved and audit-proof forever; consumable tracking stays cheap enough that people will actually do it. Cost: a small ledger drift is expected and tolerated on consumables (corrected at stocktakes, not hunted daily); adjustment movements are the one place where the ledger is edited by hand, so they carry a mandatory note and (later) land in the admin audit log.

Amendment 5 consequences: products gain a regime flag with `untracked` as the default (most of the catalog carries zero tracking burden); P5 shrinks — the qty ledger, min-stock alerts and stocktake/adjustment apply only to explicitly opted-in products; Amendment 4's consumable machinery survives but as opt-in, not baseline. New small table `equipment_shortfalls` (device, part, taken-for, PO ref, closed_at) makes cannibalization a first-class workflow with its own orders-needed hook. Bought: the app matches how the shop actually thinks — machines and debts strictly, small parts not at all; zero double bookkeeping against the audit warehouse software because this app never counts inventory value. Cost: stock availability answers only exist for products someone chose to track; the donor flow still costs mechanics two taps per cannibalization (the note-only fallback exists but loses the reminder + order hook). Rejected: sub-assembly/part-level inventory (user-refused complication), and vans-as-customers remains rejected from Amendment 3.

Amendment 6 consequences: every new table adopts the id+snapshot convention from day one (P4 deal/customer/location rows, P5 movements/equipment); product_aliases ships in P5 (customers/locations reuse the pattern later); merge tooling is deliberately simple — alias map + duplicate-suspect view + re-point action, not a fancy dedup engine. Bought: renames and merges become non-events ("just links" as the user put it); warehouse can record a one-off part/device without polluting the catalog; history stays legally frozen while master data evolves. Cost: one alias-lookup join in every name-resolving query; temp-product rows that never get promoted remain name-only forever (acceptable — most are one-off descriptions); merges are permanent by design (un-merge = manual re-split, deliberately not automated).
